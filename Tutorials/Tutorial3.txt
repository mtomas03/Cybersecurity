## Summary of the Tutorial

The tutorial outlines the mechanics, challenges, and optimization of a practical dictionary attack against a symmetric encryption payload (specifically AES-256-CBC) managed via OpenSSL.

Here are the key takeaways from the document:

* **The Scenario**: An attacker has intercepted a ciphertext and knows the cipher used (AES-256-CBC) along with its parameters. The attacker also knows the sender chose a weak password from a standard Italian dictionary.


* **The Flaw of Key Stretching**: The sender used a single iteration (`-iter 1`) for key derivation via SHA-512. While modern standards recommend hundreds of thousands of iterations to combat powerful modern GPUs, a single iteration allows an attacker to test millions of passwords almost instantaneously.


* **The OpenSSL Validation Problem**: In initial automated attack attempts (`brute-force-openssl-1.sh`), OpenSSL routinely flags incorrect passwords as "correct". This happens because OpenSSL does not validate semantic correctness; it only throws an error if the decrypted data violates PKCS#7 padding alignment rules.


* **Mitigating False Positives**: To prevent a flood of false positives, attackers must implement heuristic checks. The tutorial introduces a basic heuristic that checks for a minimum number of consecutive printable characters, though this method is imperfect and can fail depending on the file type.


* **Parallelization**: Because exploring a password dictionary is an "embarrassingly parallel problem," the execution can be significantly accelerated using the GNU parallel tool to distribute the workload across multiple CPU cores using a Master/Worker script architecture.

## Answers to the Questions in the Document

### 1. How does the number of iterations used in this derivation affect the security of the message encryption?

- 1. The concept of key stretching: A password like "password123" is easy for a human to remember, but it contains very little entropy. If we used the password directly as the key, an attacker could test millions of variations per second. Key stretching forces the computer to perform the hash function repeatedly before obtaining the final key. With -iter 1, the password passes through SHA-512 only once. It is an instantaneous operation (fractions of a microsecond). With -iter 100 000, the password is hashed, the result is re-hashed, and so on for 100 000 times.
- 2. The Impact on the Attacker (Work Asymmetry): The number of iterations creates a massive obstacle for anyone attempting a dictionary attack: For the legitimate user, waiting 0.5 seconds to derive the key and decrypt the file is not a problem. It happens only once. If the attacker has a dictionary of 1 million passwords and each attempt takes 0.5 seconds due to the high number of iterations, the attack will take 5.7 days instead of a few seconds. The higher the number of iterations, the more expensive (in terms of time and computing power) each individual attempt to guess the password becomes.
- 3. Analysis of the command in the tutorial: The -iter 1 setting is extremely insecure. With a single iteration, your "attacker" in the tutorial will be able to scan the entire dictionary almost instantly. Lack of resistance to brute-force attacks: There is no computational "brake." If the password is in the dictionary, it will be found in the blink of an eye.
- 4. Evolution of Standards: In the past, a few iterations were common. Today, guidelines recommend hundreds of thousands of iterations to counter the destructive power of modern GPUs and dedicated chips.



### 2. Why does OpenSSL report an incorrect message as correct? (Why does this happen?)

OpenSSL has no internal mechanism to verify whether a derived key is the *correct* one semantically. It simply applies the AES decryption algorithm to the ciphertext using whatever key is generated from the guessed password.

If the password is wrong, the decrypted result is 16 bytes of random chaos. OpenSSL will only trigger an error if the final byte of this chaos fails to conform to the **PKCS#7 padding standard**. If the random last byte happens to match a valid padding pattern (for instance, ending in `01`, or ending in `08` with the 7 preceding bytes also being `08`), OpenSSL assumes the alignment is correct and outputs the garbage data without an error, creating a **false positive**.

### 3. How is it possible to mitigate the problem of false positives without introducing false negatives? Do you have in mind other possible solutions?

The tutorial suggests a heuristic based on tracking consecutive printable text characters. To optimize this and avoid false negatives, alternative solutions include:

* **Magic Bytes / File Signatures**: Most common file formats (like PDF, PNG, ELF, or ZIP) start with a predictable sequence of bytes (magic bytes). The script can verify if the first few decrypted bytes match the expected header of the target file type.
* **Language/Frequency Analysis**: If the plaintext is known to be human language, you can check the decrypted output against standard letter frequencies or common Letter Pairs and Triplets.

### 4. Is the OpenSSL execution in our computer able to exploit the hardware implementation of AES provided by most modern CPUs?

**Yes, by default.** Modern versions of OpenSSL automatically leverage hardware acceleration if it is supported by the underlying CPU and enabled in the Linux kernel. OpenSSL has actually removed the ability to manually toggle or explicitly check this hardware flag inside its own command line options because it is now forced as a default optimization. To verify if it's working, you can check the Linux kernel configuration files or monitor the execution speed—hardware-accelerated decryption runs orders of magnitude faster than software-based emulation.
