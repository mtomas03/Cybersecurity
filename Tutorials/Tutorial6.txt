## Summary of John the Ripper (JtR) Tutorial

* **Overview and Importance:** Periodic verification of password quality is vital for preventing intrusions and data leaks. Passwords secure various mechanisms, including user authentication, Wi-Fi networks, and encryption key derivations. John the Ripper (JtR) is the most popular open-source tool for password cracking.


* **Installation and Compilation:** JtR is available in free and pro versions across multiple operating systems. Compilation involves configuring and making the source files. If errors arise (e.g., missing OpenSSL headers or issues with `gcc` version 11), they can be resolved by installing extra libraries or cloning the community "jumbo" version directly from the official git repository.


* **System Password Cracking:** In UNIX-like systems, user information is split between `/etc/passwd` (readable by all, contains usernames and UIDs) and `/etc/shadow` (privileged access, contains salted/hashed passwords). JtR provides a tool called `unshadow` to combine these files into a single input file for cracking.


* **Cracking Modes:**
* *Single Crack:* Tries variations of the username; very fast but only catches extremely weak passwords.


* *Wordlist:* Uses a dictionary file of common words; performance depends on the dictionary size and relevance (e.g., localized culture).


* *Incremental:* A brute-force exploration of all possible character combinations. It can be optimized by setting character frequencies or length limits, though it often takes too long to finish.


* *Wordlist with Rules:* Combines dictionaries with common human password variation rules, such as adding numbers or symbols.


* *Default:* Running JtR without specifying a mode executes these approaches in an optimized order based on probability and time efficiency.




* **PDF Cracking:** JtR can evaluate passwords protecting PDF files. Because it cannot read PDFs directly, the companion script `pdf2john.pl` must first extract the embedded hash into a text file before JtR processes it.


* **GPU Acceleration:** Password cracking is highly parallelizable, and modern GPUs significantly speed up the process. However, JtR has limited GPU support; dedicated tools like Hashcat are better suited for GPU-based cracking.

## Answers to Document Questions

### 1. Which password is more secure concerning password cracking?

The second password (`ThaliX_J_18/05/2008`) is significantly more secure because even though the first password uses a diverse set of character types, its length is only 6 characters. Short passwords are highly vulnerable to "Incremental" (brute-force) attacks because the total combination space is small enough to be exhausted rapidly. The second password is 19 characters long. Even though it contains predictable components like a date, its sheer length exponentially increases the computational complexity, making brute-force exploration practically impossible in an acceptable timeframe.

### 2. Is it really necessary to have the hashed password included in the PDF, and why did designers include it?

Strictly speaking, it is not mathematically mandatory to include a separate, explicit validation hash just to decrypt a file, but it is standard practice for user experience and system efficiency.

Designers include the validation hash so that PDF reader applications can instantly verify if the user has entered the correct password before initiating any heavy cryptographic operations. The user-provided password undergoes a hash function to derive the symmetric AES encryption key. By comparing the input hash to the stored hash, the system can immediately reject wrong entries.

### 3. What would be the consequences of not including the hashed password in the PDF?

If the hashed password were omitted from the PDF file, it would result in the following consequences:

* **Performance Degradation for Users:** The PDF reader would have no way to verify the password upfront. It would be forced to attempt to decrypt the document data using an encryption key derived from whatever password the user typed. For large PDF files, this processing would cause annoying performance delays every time a typo is made.


* **Slower Offline Cracking:** From a security standpoint, an attacker would no longer be able to use tools like `pdf2john.pl` to isolate a tiny, lightweight hash string for rapid offline cracking. Instead, to test each password guess, the cracking software would have to decrypt actual blocks of the PDF content and check if the resulting data forms a valid, corruption-free PDF structure. This would drastically slow down the speed of password-cracking attempts.
